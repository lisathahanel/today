Cloudflare Monetization Gateway: How It Works

How to charge AI agents and other clients for access, all inside a single HTTP request

Imagine you run an API, a dataset or an MCP server, and AI agents keep showing up to use it. What if you could charge them automatically, with no checkout page and no separate billing call? That's the idea behind Cloudflare's Monetization Gateway.

According to the information provided, Monetization Gateway is a Cloudflare product in closed beta that launched on September 30, 2026. It lets you charge AI agents and other clients for access to your domain, API, datasets or MCP server, with the payment handled entirely inside the HTTP request.

It's built on the x402 protocol (version 2), an HTTP-native payment standard. Buyers never get sent to a checkout page or make a separate payment API call. Payments are authorized cryptographically and settled in the same request and response cycle.

Before you read on: This is a beta product, and details like availability and eligibility can change. Check Cloudflare's current documentation before you plan around it.

What Can You Protect With It?

You can use Monetization Gateway to protect APIs, Model Context Protocol (MCP) tools, sites and datasets. Payment rules apply to matching traffic, and you decide what "matching" means. You can match requests by URL, headers, query parameters or caller attributes. A rule can charge every caller, or only verified bots, for instance.

How the Payment Flow Works

Here's the whole thing step by step, with the actual requests so you can see what's happening.

Step 1: The client asks for a resource without paying

A buyer, usually an AI agent, requests a protected resource like any other:

GET /premium-data HTTP/1.1
Host: api.example.com

Step 2: The gateway answers with "402 Payment Required"

Monetization Gateway intercepts the request because it matches one of your payment rules. It replies with a 402 Payment Required status and a PAYMENT-REQUIRED header. That header holds Base64-encoded JSON describing the resource and the accepted payment options: the scheme, network, asset, amount, your receiving wallet and the maximum timeout.

HTTP/1.1 402 Payment Required
PAYMENT-REQUIRED: <BASE64_ENCODED_PAYMENT_REQUIRED>

After Base64 decoding, a fixed-price response has this general structure:

{
  "x402Version": 2,
  "resource": {
    "url": "https://api.example.com/premium-data",
    "description": "Premium data",
    "mimeType": "application/json"
  },
  "accepts": [
    {
      "scheme": "exact",
      "network": "<CAIP_2_NETWORK>",
      "asset": "<ASSET_IDENTIFIER>",
      "amount": "25000",
      "payTo": "<RECEIVING_WALLET>",
      "maxTimeoutSeconds": 3600,
      "extra": {}
    }
  ]
}

The accepts array tells the client how it can pay. These are the important fields:

Field Description
schemeThe payment scheme. Monetization Gateway uses exact for fixed pricing and upto for variable pricing.
networkThe blockchain network identifier, in CAIP-2 format.
assetThe asset identifier used for payment.
amountThe fixed charge, or the maximum authorized charge, in atomic units.
payToThe receiving wallet you configured as the seller.
maxTimeoutSecondsThe maximum time allowed for payment authorization.

Step 3: The client signs a payment and retries

The client picks one of the accepted options and signs a payment authorization from its wallet. Then it repeats the request with a PAYMENT-SIGNATURE header:

GET /premium-data HTTP/1.1
Host: api.example.com
PAYMENT-SIGNATURE: <BASE64_ENCODED_PAYMENT_PAYLOAD>

The signed payload ties the authorization to the payment requirements the client selected. Use an x402 client library to create this payload instead of building it by hand. To build a paying client, look up Cloudflare's x402 payments documentation. To pay from a Cloudflare Agent, see the Pay from Agents SDK documentation.

Step 4: The gateway verifies the payment and calls your origin

The gateway checks that the authorization is valid, then forwards the request to your origin server. It adds a PAYMENT-CONTEXT header containing a signed JSON Web Token (JWT), so your origin can validate the payment before it serves anything.

Important: Your origin must validate the PAYMENT-CONTEXT token before serving the paid resource. Origins using variable pricing also return the actual charge in a PAYMENT-SETTLEMENT header. These headers are between Monetization Gateway and your origin. They are not x402 client headers.

Step 5: The gateway settles the payment and returns the resource

Your origin produces a response, and the gateway settles the payment through the Coinbase x402 Facilitator. For fixed pricing, it settles the signed amount. For variable pricing, your origin reports the actual amount. After successful settlement, the buyer gets the resource.

If verification or settlement fails, the gateway doesn't serve the protected resource. Clients should check the HTTP status and the x402 response before retrying.

The two client-facing headers at a glance

x402 uses two headers on the client side, and each one carries Base64-encoded JSON:

Header Direction Purpose
PAYMENT-REQUIREDGateway to clientDescribes the resource and accepted payment options.
PAYMENT-SIGNATUREClient to gatewayProvides the signed payment authorization.

What You Configure as the Seller

Everything is controlled by monetization rules. Each rule decides which matching requests need payment, and it defines a domain, a URL, a price and an audience. Here's what goes into one:

  • Domain and URL to match: you can also match on headers, query parameters and caller attributes.
  • Audience: Everyone, or Verified Bots.
  • Pricing scheme: Fixed or Variable.
  • Price: between $0.001 and $100.
  • HTTP methods: GET by default, with multiple methods selectable.
  • Receiving wallet: where the payments are sent.

Choose a pricing scheme

Pick the scheme based on when you figure out the charge.

Scheme x402 scheme Behavior
FixedexactCharges the same price for each request with fixed inputs. The gateway settles the signed amount.
VariableuptoAuthorizes a maximum price. Your origin discloses and settles the actual amount.

Enter a price (and understand atomic units)

Prices and settlements use atomic units. One atomic unit equals $0.000001. Here are a couple of handy conversions:

Amount Atomic units
$0.0011,000
$0.0110,000
$100 (maximum price)100,000,000

The minimum settlement amount is $0.001, or 1,000 atomic units. The maximum price is $100, or 100,000,000 atomic units. That also explains the "amount" of 25000 in the example above: 25,000 atomic units works out to $0.025.

Select an audience

Audience Behavior
EveryoneCharges all traffic matching the URL and advanced conditions.
Verified BotsCharges matching bots identified through BotBase.

Choose HTTP methods

By default, a rule charges GET requests. You can select multiple HTTP methods for a single rule.

Add conditions

How to Set Up Your First Rule

Ready to try it? Here's the setup, in order.

First, review the prerequisites

  • Your account and zone meet the eligibility requirements.
  • You have a receiving wallet.

Then configure a payment rule

  1. In Monetization Gateway, select the domain you want to monetize.
  2. Select the receiving wallet for payments.
  3. Enter the URL for the request you want to monetize.
  4. Select an audience: Everyone to charge all matching traffic, or Verified Bots to charge bots identified by BotBase.
  5. Select a pricing scheme: Fixed to charge the same amount per request, or Variable to authorize a maximum amount (you must report the actual amount to finish the transaction).
  6. Enter the price. The minimum is $0.001.
  7. For advanced settings, look at the monetization rules documentation.

Don't skip the last step: To complete configuration, Cloudflare strongly recommends that you verify payment at your origin by validating the PAYMENT-CONTEXT token.

Key Constraints to Know About

  • Closed beta: you have to request access in the dashboard.
  • US-only: both buyers and sellers must be based in the United States.
  • Origin validation: Cloudflare strongly recommends validating the PAYMENT-CONTEXT JWT at your origin before serving paid resources.

Final Thoughts

Monetization Gateway turns a normal HTTP request into a paid transaction. The client asks, the gateway says "pay first," the client signs and retries, and your origin serves the resource once the payment checks out. You set the rules, the price and the wallet, and the gateway handles the payment flow.

It's still a closed beta limited to US-based buyers and sellers, so confirm current availability before you build on it. If you do get access, start with one simple fixed-price rule, validate the payment token at your origin, and expand from there.

Final Reminder

Request payment, verify the signature, validate at your origin, and only then serve the resource.
